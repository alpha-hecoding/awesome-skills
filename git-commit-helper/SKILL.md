# Git 提交助手

把本次任务产生的变更整理成干净、语义清晰的提交。核心目标：让每一条 `git log` 记录都能在十秒内读懂"改了什么、属于什么性质"。

## 安全边界（最高优先级）

- **绝不自动提交。** 只有用户在本次对话中明确说过"提交/commit"才执行；含糊的"先弄完"不算。这与全局 CLAUDE.md 的约束一致。
- **绝不 `git push`。** 本技能止步于 commit。用户单独明确要求 push 时才 push。
- **绝不 `git add -A` / `git add .`。** 逐文件显式 add（整目录新增可用 `git add <目录>/`），避免误提交无关文件。
- 发现疑似敏感文件（密钥、`.env`、凭据、生产配置含密码）或垃圾文件（`__pycache__`、`.venv`、临时产物、编辑器备份）出现在待提交列表里：停下来，向用户指出并确认处理方式，不要静默提交。

## 工作流程

### 1. 弄清"本次任务的变更"是哪些

提交范围 = 本次任务造成的变更，而不是工作区里所有脏东西。

```bash
git status --short          # 全貌：哪些文件被改/新增/未跟踪（首列为 M 表示已暂存）
git diff --cached --stat    # 暂存区是否已有内容
```

对照对话上下文判断每个文件的归属。工作区里常有与本次任务无关的遗留改动（用户自己改的、上个任务残留的）——那些**不碰**，留在工作区，并在最后汇报时提一句"以下文件未纳入提交"。

- 暂存区已有与本次任务无关的内容：停下来向用户确认处理方式（`git restore --staged <文件>` 移出暂存，或单独提交），**不要让它被本次 commit 顺带带进去**。
- 单个文件里混有本次任务改动与用户无关改动：先向用户确认，用户同意后用 `git add -p` 只暂存本次任务的代码块。
- 拿不准某个文件该不该提交时，问，不要猜。

### 2. 判断是否拆分多次提交

本次任务如果分多个阶段执行、每阶段目标独立明确（例如：先"优化报表SQL性能"再"更新口径文档"；或"先修 bug 再加导出功能"），就**按阶段拆成多次提交**，每次单独 add 该阶段涉及的文件再 commit。判断标准：

- 拆开后每条提交能否独立讲清一件事？能拆就拆。
- 两批文件服务于两个不同意图（一个 fix 一个 feat）？拆开。
- 一次逻辑改动顺带产生的关联修改（如改口径同时改了对应文档）？**不拆**，放同一条。

### 3. 写提交信息

格式：`类型: 一句话简述`（中文，全角冒号亦可，跟随仓库现有风格——先 `git log --oneline -5` 看一眼）。

类型选择：

| 类型 | 用于 |
|---|---|
| `feat` | 新功能、新报表、新脚本、新指标 |
| `fix` | 修 bug、修正错误口径、修 SQL 逻辑错误 |
| `refactor` | 不改外部行为的调整：改名、结构整理、列名调整 |
| `perf` | 性能优化（如慢 SQL 优化、索引调整） |
| `docs` | 仅文档/口径说明变更 |
| `chore` | 杂务：配置、忽略规则、依赖升级等 |
| `test` | 仅测试变更 |

简述要求：

- 一句话，动宾结构，直接说干了什么。约 30 字以内为宜。
- 确切覆盖内容但不罗列细节：报表类改动带上报表编号（如"报表162/147/148"），不用写"修改了3个文件"。
- 禁止空话（"更新代码"、"一些修改"、"完善功能"）；禁止正文长段落；禁止多余信息。

**示例：**

Input: 本次为报表31新增了催回率指标列，并同步更新了对应口径文档
Output: `feat: 报表31新增催回率指标列及口径文档同步`

Input: 修复了还款计划查询漏排除已取消账单导致逾期统计偏高的问题
Output: `fix: 修复已取消账单未排除导致逾期统计偏高`

Input: 任务分两阶段——先优化报表11慢SQL，再单独整理导出脚本参数校验
Output（两条）:
```
perf: 报表11渠道流量监控SQL性能优化
fix: 导出脚本补充批次参数校验
```

### 4. 执行提交

每个提交单元：

```bash
git add <文件1> <文件2> ...      # 显式逐个列出（整目录新增可用 `git add <目录>/`）
git diff --cached --stat          # 核对暂存内容与本次意图一致
git commit -m "类型: 一句话简述"
```

多个提交单元时循环"add → 核对 → commit"，保持每次暂存区干净、只含该阶段文件。

### 5. 收尾汇报

提交完成后向用户简要汇报：

- `git log --oneline` 列出刚产生的提交；
- 未纳入提交的工作区遗留文件（如有）；
- 明确说明**未执行 push**。

## 异常处理

- 工作区干净（没有本次任务的变更）：告知用户无可提交内容，不动 git。
- 提交被 pre-commit hook 拦截（lint/commitlint 校验、锁文件等）：如实汇报错误内容，**未经用户明确要求不得用 `--no-verify` 绕过**。
- 仓库有冲突、merge 中间态、detached HEAD：停下来报告现状，等用户指示。
- 用户指定的文件在 git 状态里不存在：如实说明，不伪造提交。
- 误 add 了文件：用 `git restore --staged <文件>` 移出暂存，禁止用 `git reset --hard` 等破坏性命令回退。
